# EX13 scoped corrections

`proposeCorrection`, `answerQuestion` and `undoCorrection` accept the strict reserved EX02 request schemas plus a private verified request context. They use the existing SERIALIZABLE mutation boundary, current World access, operation identity, SQL-only writers, domain locks, receipts and outbox. `SemanticExecutor.executeCorrection(credential, bytes)` runs their explicit cases in the same dispatcher and Presence/deadline/disclosure path as D01. `execute` still accepts only D01 envelopes; no correction HTTP route is published here.

A proposal loads the original principal/purpose/World-bound Frame and validates its exact obligation and civil interval. A selected claim must be Known, present in that Frame and cover the whole proposed interval. Empty/unknown-time scope does not grant an arbitrary correction target. Equal or disjoint active correction intervals are supported; overlapping unequal intervals return Unsupported. They are not silently merged or broadened.

The Question binds the exact released `{ frameRef, consequence }` digest and allowed answers. The Case stores the retained Frame basis with only its own known cases increment advanced to the post-proposal cut. Its read set, source dependencies and released consequence remain unchanged. This avoids immediately invalidating the question by its own insertion without renewing consent. Answer validates that retained base before writing; a later relevant import yields Stale, without replacing the stored question or recomputing an answer against fresh claims. Replay still reauthorizes and uses the original receipt before obsolete guards are considered.

Answer `confirm` applies the stated choice; answer `unknown` applies an explicit unknown for that same interval and never selects a source. `scopedCorrections` is a separate annotation in the saved Frame. Claims, automatic selection, contestation and unverified status remain source observations. September approval does not resolve October or another obligation. Authorship `current-principal` is valid only for this principal-bound, owner-private profile; extending sharing requires revisiting projection and disclosure.

Corrections are append-only. Every event has the exact next cases revision as PostgreSQL BIGINT, passed as a decimal string via BigInt. An Answer links the previously effective Answer in its exact scope. Undo links the currently effective Answer being retracted; projection restores that target's predecessor, or no decision. Undo creates its own correction reference, receipt and outbox; it does not delete/update an old correction, receipt or Frame. The returned Undo reference names the retraction event; subsequent actions use the effective correction reference from a fresh Inspect.

`schema.sql` is a candidate delta, not a numbered migration. It adds the saved Case basis, event revision and constraints permitting one Answer per Case and one Undo per target. Root owns numbered migration 003 and production/test composition. Before enabling this handler, Inspect's database must include the delta. There is no schema-detection fallback. Existing pre-EX13 Cases/events do not exist in this new profile; the candidate does not rewrite deployed history.

Tests use the real restricted PostgreSQL authority role, S3 adapter and, for the executor, Better Auth signup/session/logout. Pure tests exercise response classification, subject/claim/interval validation and overlap limits. Integration covers September/October and another obligation, concurrent identical answer identity, unknown, both undo transitions, retained Frames, receipt authorship, altered consequence, stale dependency, another identity and post-logout replay. Root composition and independent review remain separate acceptance gates.

EX25: handlers bind the request and check reauthorized receipt replay before decoding retained Frame/Case state. The commit repeats replay under its existing locks. Valid five-domain bases stay readable, but a new proposal/answer/undo requires a fresh v2 basis; legacy new acts return `Stale` before scope/target mutation checks. The proposal adjusts only its own cases increment after the current-basis guard. Applied literal corrections and historical receipts are preserved; identity is not inherited across subjects by this change.
