# Identidade D01 — EX09

Candidato em qualificação, ainda não aceito nem montado no servidor. Better Auth 1.7.2 e pg 8.23 são componentes reais; o adapter não implementa senha, assinatura, sessão ou criptografia próprias.

`makeD01IdentityLayer({baseUrl, databaseUrl, secret, sessionSeconds})` fornece `Presence` e `D01Auth`. URL do banco e secret usam `Redacted`; secret precisa ter 32–1024 caracteres e deve ser gerado criptograficamente pela instalação, sem valor padrão. `baseUrl` é uma origem HTTPS exata, ou HTTP em loopback para o perfil local. Sessões duram entre um segundo e sete dias, conforme configuração explícita, sem renovação automática.

`D01Auth.handle(Request)` retorna `Effect<Response, Unavailable>` e encaminha apenas POST sign-up/email, sign-in/email, sign-out e GET get-session em `/api/auth` ao handler oficial. A URL deve coincidir com a origem configurada; Origin divergente é recusada. A biblioteca mantém suas verificações reais de CSRF, Fetch Metadata e callback. Proxy headers não definem a origem. O transporte deve preservar URL e headers do request. Outros fluxos de identidade não estão publicados por este adapter.

`Presence.verify` recebe o header Cookie inteiro como `Redacted`, não um principal nem um bearer UUID. Consulta `auth.api.getSession` com `disableCookieCache` e `disableRefresh` a cada chamada; não há sessão offline. Valida o resultado do provider com Schema e converte seus instantes com DateTime. `principalId` é o UUID persistente de `identity.user.id`, gerado pelo PostgreSQL por configuração suportada de Better Auth; email ou header de ator nunca fazem esse mapeamento. `sessionId` é `session.id`, distinto de `session.token`. A presença sempre pertence a live e não cria membership ou grant.

Email/senha prova controle da conta local mediante sua credencial. O perfil não verifica posse do endereço de email: `emailVerified` permanece falso e não há envio SMTP fictício. A senha usa a implementação da biblioteca. Cookies são HttpOnly, SameSite=Lax e host-only; HTTPS ativa Secure. Nenhum teste de atributos do cookie constitui prova de TLS ou do navegador.

O pool pertence ao Scope e usa search_path=identity. O mesmo pg.Pool é admitido pelo guard PostgreSQL EX06 e por uma verificação adicional que recusa USAGE de authority/jobs, inclusive por SET ROLE. Better Auth só recebe esse pool. A admissão também exige cada uma das quatro permissões SELECT/INSERT/UPDATE/DELETE em cada uma das cinco tabelas identity; USAGE isolado não basta. `D01Auth.checkHealth` repete a mesma admissão no pool existente, sem conceder privilégios ou criar outro pool. `schema.sql` foi gerado com `getMigrations/compileMigrations` da versão instalada; contém user/session/account/verification/rateLimit. Aplicar em transação pelo migrator depois de EX06 e executar `grantD01IdentityRole`. Root reserva numeração e composição; runtime não migra.

O rate limiter oficial está habilitado com armazenamento PostgreSQL. Nenhum header de IP do cliente é confiado neste perfil: em desenvolvimento a biblioteca usa localhost; em produção sem IP confiável usa bucket compartilhado por caminho. Uma instalação com limite por origem de rede requer uma borda de proxy/IP qualificada. Mensagens e argumentos de log da biblioteca podem conter SQL ou dados do request; o adapter transmite somente severidade e evento fixo. Falhas públicas de provider são Unavailable fechado.

Dez testes de integração exercitam cadastro/login/logout, ausência de grant, UUIDs e separação de token, senha inválida, expiry com relógio real, audience/origin/callback/CSRF, flags Secure, outra conta e headers forjados, negação SQL sem cache e credencial SQL de outra função. PostgreSQL é real; requests usam o handler Fetch oficial em processo. A composição com SemanticExecutor e PostgreSQL/S3 reais comprova genesis/replay, negação uniforme de outro principal ou membership revogada e logout. Um lock advisory real mantém a operação em voo durante logout: o commit persiste um mundo/receipt, mas a pré-emissão retém a resposta como Unauthenticated. O limiter retorna 401 nas três primeiras senhas incorretas e 429 na quarta, com registros persistidos. A introspecção oficial getMigrations encontra zero tabelas, colunas ou índices pendentes e nenhuma mudança insegura. Revisão independente ainda pendente. HTTP montado/navegador pertencem à integração de EX10/EX15.

## Logout revocation proof

Better Auth 1.7.2 can return 200 after swallowing a session deletion error. The sign-out bridge resolves the signed cookie with the provider before handling the request, then checks absence of that exact authenticated session ID through the same identity pool before forwarding a successful response. A failed lookup, failed post-check, or surviving row returns `503 { code: "UNAVAILABLE" }` without forwarding cookie deletion, so the client can retry. Provider validation and CSRF statuses remain intact; an already absent session remains idempotent. No authority query, new grant, or parallel session policy is introduced.

`logout.EX09.integration.test.ts` uses real PostgreSQL and Better Auth. The DELETE-denial regression first failed with actual 200 while the same session remained usable, then passed with 503. Further cases exercise a real trigger that silently retains the session, SELECT privilege loss, provider callback rejection, an untrusted body session ID, successful retry and already absent logout.

Validation on 2026-09-05: all nine identity integration files passed (15 tests) with one worker against real PostgreSQL; TypeScript and focused oxlint passed.
